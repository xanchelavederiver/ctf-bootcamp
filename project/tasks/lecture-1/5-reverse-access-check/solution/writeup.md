# Разбор: Пропуск (reverse)

Утилита `access-check` читает строку и печатает `Access granted` или
`Access denied`. Рабочих пропусков три, и каждый спрятан своим способом.

Сначала посмотрим, что это за файл:

```console
$ file access-check
access-check: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically
linked, interpreter /lib64/ld-linux-x86-64.so.2, for GNU/Linux 3.2.0, not stripped
```

`not stripped` — таблица символов на месте, обратная разработка будет проще.

## Флаг 1 — печатные строки

Первый пропуск сравнивается с константой, то есть лежит в файле открытым текстом.
Его видно утилитой `strings`:

```console
$ strings access-check | grep BootCTF
BootCTF{str1ngs_unlock_the_d00r}
```

Проверим:

```console
$ echo 'BootCTF{str1ngs_unlock_the_d00r}' | ./access-check
Access granted
```

**Чему учит.** Самый первый шаг статического анализа — печатные строки. Пароли,
ключи и флаги, записанные в коде константой, находятся мгновенно.

## Флаг 2 — отладчик и конструктор

В выводе `strings` второго флага нет: он хранится зашифрованным. В программе есть
функция с атрибутом `constructor` — она выполняется **до** `main` и расшифровывает
флаг в памяти. Сравнение идёт вручную, поэтому `ltrace` не покажет аргументов
`strcmp`. Проще всего остановиться в начале `main`, когда конструктор уже отработал,
и прочитать расшифрованный буфер `dec2`:

```console
$ gdb -q ./access-check
(gdb) break main
Breakpoint 1 at 0x401502
(gdb) run
Breakpoint 1, 0x0000000000401502 in main ()
(gdb) x/s &dec2
0x4040e0 <dec2>:	"BootCTF{gdb_sees_the_c0nstruct0r}"
```

```console
$ echo 'BootCTF{gdb_sees_the_c0nstruct0r}' | ./access-check
Access granted
```

**Чему учит.** Если секрета нет в файле, он появляется во время работы. Код,
выполняющийся до `main` (конструкторы, инициализация) — обычное место для такой
«распаковки». Динамический анализ в отладчике показывает значения, которых нет в
статике.

## Практика

Похожие задания — категория Reverse Engineering на учебных площадках (например,
picoCTF/picoGym) и наборы crackme. Полезно потренировать `gdb`: точки останова,
просмотр памяти (`x/s`, `x/16xb`), регистры (`info registers`).

## Домашнее: Флаг 3 — цепочка if-ов

Третий пропуск не виден ни `strings`, ни в `gdb`: его нигде нет целой строкой.
Функция `check3` проверяет ввод по одному символу, отдельным `if` на каждый, а
условия в коде перемешаны. В дизассемблере каждое условие выглядит так:

```console
$ objdump -d access-check | sed -n '/<check3>:/,/ret/p'
  ...
  mov    -0x18(%rbp),%rax      # указатель на введённую строку s
  add    $0x20,%rax            # s + 0x20  ->  символ с индексом 32
  cmp    $0x7d,%al             # сравнение с 0x7d = '}'
  ...
```

Смещение в `add` — это индекс символа, а константа в `cmp` — его код. Проверка
длины в начале функции (`cmp $0x21,%rax`, где 0x21 = 33) говорит, что флаг из 33
символов. Собрав все пары «индекс → символ» и упорядочив их по индексу, получаем
третий флаг. Это удобно автоматизировать (см. `solve.py`), но на занятии задача —
проделать разбор руками, в том числе в декомпиляторе (Ghidra) как псевдокод.
